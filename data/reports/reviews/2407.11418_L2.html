S Core Contribution

The paper introduces semantic operators, a declarative programming interface that extends the relational model with composable AI-based operations (filter, join, topk, aggregation, map, extract, search, cluster) parameterized by natural language expressions (langex). These operators are implemented in LOTUS, an open-source query engine with a Pandas-like API that provides multiple algorithms and optimizations per operator, including model cascades with log-probability-based scoring, semantic index-based optimizations, and approximate join algorithms (map-search-filter, search-filter patterns). F Mapping to Dr. Lan's 7-Layer Semantic Filter Framework

1. Data Representation Layer

LOTUS extends the relational model with tables containing both structured data columns and unstructured free-form natural-language text columns. Semantic similarity indices (embeddings via FAISS) can be created over text columns to enable efficient semantic query processing. The data model uses a Pandas DataFrame representation. Section 2.1

2. Candidate Executor / Proxy Layer

LOTUS supports configuring multiple LMs (e.g., TinyLlama/Llama-8B as proxy, Llama-70B/GPT-4o as oracle) for model cascades. Embedding models (e.g., E5Model, ColBERT) serve as lightweight retrieval proxies for similarity-based operations. Cross-encoder re-rankers (e.g., MixedBread) provide intermediate-cost executors. Section 3.1.1, Section 4

3. Unit of Decision Layer

The unit of decision varies by operator: sem_filter and sem_map operate per-row; sem_join evaluates per-pair of rows; sem_topk performs pairwise comparisons between document pairs; sem_agg reasons over groups of rows. Each operator defines its own granularity of LM invocation. Section 2.2, Section 3

4. Predicate Transformation Layer

User-specified langex expressions are automatically wrapped in operator-specific instruction prompts managed by the system (e.g., the filter prompt instructs the model to output 'True' or 'False'). The system handles prompt construction transparently and can leverage prompt optimization techniques (e.g., DSPy). Demonstrations can be optionally provided. Section 2.1.2, Section 3.1 (Figure 17)

5. Calibration / Sampling Layer

For model cascades in sem_filter and sem_topk, LOTUS computes confidence scores by exponentiating the log-probabilities of the output tokens corresponding to True/False labels. A user-defined confidence threshold determines which records are routed to the oracle model. This is a lightweight, operator-semantics-aware scoring function. Section 3.1.1

6. Routing / Action Layer

Records with confidence below the threshold are routed from the proxy to the oracle LM. For joins, the system selects among nested-loop, map-search-filter, or search-filter algorithms based on table size and user-specified LM call budget. For topk, the system chooses among quickselect, heap, or quadratic algorithms. Semantic index optimizations are applied when correlation exists between embeddings and the ranking criteria. Section 3.1.1, Section 3.2, Section 3.3

7. Guarantee Layer

LOTUS does not provide formal accuracy or recall guarantees. The system relies on empirical evaluation across applications to demonstrate quality. Approximate join algorithms trade off completeness for efficiency. The confidence threshold in cascades is user-specified without formal bounds on accuracy loss. Section 4

M Method Components
Semantic Operators

A set of declarative operators (sem_filter, sem_join, sem_sim_join, sem_agg, sem_topk, sem_map, sem_extract, sem_cluster_by, sem_search, sem_index) that extend the relational model with AI-based operations. Each operator takes a parameterized natural language expression (langex) that specifies the semantic operation (predicate, comparator, aggregation, or projection) in natural language. Section 2, Table 1

Model Cascade Optimization for sem_filter

Uses a lightweight scoring function based on exponentiated log-probabilities of the True/False output tokens from a cheap proxy LM. Records with confidence below a user-defined threshold are routed to a larger oracle LM. This avoids the overhead of fine-tuning a separate scorer or re-sampling from the proxy model. Section 3.1.1

QuickSelect-based sem_topk Algorithm

Implements pairwise LM-based comparisons aggregated via a quick-select-based top-k ranking algorithm. Each round selects a pivot, compares all remaining elements to the pivot in a fully parallelizable batch, then recurses. This provides high accuracy with at least an order of magnitude fewer LM calls than quadratic sorting and more batching opportunities than heap-based approaches. Section 3.2.1, Section 3.2.2

Semantic Index-based Pivot Selection

For sem_topk, LOTUS can leverage the semantic similarity index to optimize pivot selection by sorting documents based on embedding distances and selecting the (k+ε)-th item as the first pivot, reducing subsequent LM comparisons when correlation exists between semantic similarity and the user's ranking criteria. Section 3.2.3

Approximate Semantic Join Algorithms

Three join patterns: (1) nested-loop join with batched LM processing (O(N1·N2) calls), (2) map-search-filter pattern that first performs an LM projection over the left key, then similarity search, then filter (O(N1·K) calls), and (3) search-filter pattern that performs similarity join then filter (O(N1·K) calls). The approximate patterns reduce LM calls by up to 800× compared to naive join. Section 3.3.1

Hierarchical Reduce Aggregation

For sem_agg, LOTUS implements a hierarchical reduce pattern that recursively aggregates input data to produce partial answers until a single answer remains, allowing greater parallelism. Users can override with sem_partition_by to specify custom groupings (e.g., semantic clustering) for improved aggregation quality. Section 3.4

Parameterized Natural Language Expressions (langex)

A core abstraction where users write natural language expressions parameterized by data columns (indicated in double brackets). The langex function varies by operator (predicate for filter, comparator for topk, aggregation for agg, projection for map). This separates the logical query plan from its implementation.
